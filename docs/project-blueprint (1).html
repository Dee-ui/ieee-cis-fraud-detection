Why the split exists

config/One place for every path and setting. Fix a wrong path once, not in fifteen files.
data/Four stages, one folder each. Raw is never edited, so everything downstream can always be rebuilt from a known start.
scripts/Things you run once in a while. Keeping them out of src/ keeps the pipeline folder focused.
src/utils/How individual things are done. Small, testable, reusable.
src/pipelines/What happens in what order. Short enough to read the whole flow on one screen.
src/features/Its own package because the transformer is too large to be called a utility.
models/Large binaries, kept out of version control, easy to mount into a container later.
reports/Output meant for humans, as opposed to models/ which is read by machines. Small enough to commit.
docs/Documentation as a deliverable, travelling with the code rather than living in a chat.
notebooks/Exploration only. Anything that matters gets rewritten as a proper module.

01

The engine underneath everything

Every phase ran the same five moves. Once you see the loop, the rest of this document is the loop repeated with different content and different files falling out of it.

MOVE 1Name the gap

Write down what you do not know. As a question with an answer you could go and find.

MOVE 2Go measure it

Write a small piece of code that answers it and prints the number. Do not reason from memory.

MOVE 3Read what came back

Including the parts you did not expect. Surprises are where the real decisions hide.

MOVE 4Decide, and say why

Give the decision a number, put the evidence beside it, and write the file that implements it.

MOVE 5Lock it and move on

The number becomes a checkpoint. Later stages recheck it, so a break shows up immediately.

Anything you could not answer becomes a numbered open question, tagged with the phase that will need it. Nothing gets forgotten and nothing gets guessed.

The phases, and the files each one produced

Each case file reads the same way: what we knew, what we did not, the check we ran, what came back, what changed. Then a ledger of every file created and every file changed, with the reason. The strip at the bottom shows the facts locked in by the end of that phase. Watch it grow.

Phase 0. Choosing what to work on

Before any code
What we knew
  • An earlier attempt at the same problem had stalled. The model would not improve whatever technique was tried.
  • That dataset had 193 fraud cases inside 9,940 rows.
What we did not know
  • Whether the ceiling was the method or the data.
  • What a dataset needs to look like for the problem to be worth solving properly.
The check we ran

We wrote down what the project needed to demonstrate, then looked for data that would force us to demonstrate it: enough real fraud to learn from, more than one table so there is a genuine join, and a test set separated in time so the hard lesson about validation cannot be dodged.

What came back
  • 20,663 fraud cases in 590,540 rows. Roughly a hundred times more examples of the thing we are detecting.
  • A second table of device information matching only some transactions.
  • A test period starting a month after training ends.
What changed because of it

The project became possible at all, and it set the habit for everything after: choose your inputs by the shape of the problems you want to be forced to solve, not by the topic. Every awkward property of this data later became one of the most interesting parts of the work.

Locked in after this phase
enough positive cases a real join to handle a future test period

Phase 1. Proving the data before trusting it

Foundations
What we knew
  • The published row and column counts for each file.
  • Our own machine and platform.
What we did not know
  • Whether the download was complete and matched what was published.
  • Whether the identifier linking the two tables is unique, which decides whether a join is safe.
  • How much of the second table actually matches the first.
  • Where the project folder would eventually live.
The check we ran

Before touching the data, we wrote a script whose only job is to prove the data is sound. Five checks: every file present and not empty, row and column counts against the published figures, the fraud rate roughly as advertised, no duplicate identifiers, and consistent column spelling across files. It reads one column at a time rather than loading whole files, so it costs seconds instead of gigabytes.

What came back
  • Fraud rate 3.4990%. Every shape matched exactly.
  • Zero duplicate identifiers in either table.
  • Only 24.4% of transactions have a matching record in the second table.
  • Test files spell a set of columns with a hyphen where training files use an underscore.
What changed because of it
  • Those numbers became permanent checkpoints, recomputed by every later stage.
  • Because the identifier is unique, the join could be set to fail loudly if that ever stopped being true.
  • The spelling difference became a deliberate rename step instead of a confusing bug later.
  • Because the folder location was unknown, no path was ever written by hand. That paid off twice: once when the folder name did not match the repository, once when the whole project was moved.

Phase 2. Understanding before touching

Exploration
What we knew
  • The verified counts from phase 1.
  • That most columns are anonymised and their meaning will never be published.
What we did not know
  • Whether three quarters of the second table being missing is damage or information.
  • Whether time matters, and how.
  • Whether 339 unnamed columns have any structure at all.
  • Which measure of success would actually tell us if the model is any good.
The checks we ran
  • Sorted every column into a family by a naming rule, and made the code shout if anything did not fit a known family. Nothing was allowed to slip through unclassified.
  • Compared the time range of training against test.
  • Fingerprinted each column's pattern of blanks rather than counting them. For every column, a true or false list of which rows are empty, then hashed. Same fingerprint means blank on exactly the same rows.
  • Measured the fraud rate inside every category, with a minimum group size so a category of three transactions cannot shout louder than one of three hundred thousand.
What came back
  • Training covers December to May, testing July to December. A deliberate 30 day gap and no overlap.
  • The 339 unnamed columns fall into exactly 15 blocks that go blank together. Eight of those weave through each other's numbering.
  • Two blocks are both 86.12% empty but in different rows. Counting blanks would have merged them.
  • Categories separate strongly. One product runs at 11.69% fraud while another runs at 2.04%.
What changed because of it
  • Validation became time based. Shuffling would let the model learn from the future and be graded on the past.
  • Accuracy was dropped entirely. A model that says "never fraud" is right 96.5% of the time here.
  • Blanks stay blank. The models we intend to use learn a direction for missing values on their own.
  • The plan for cutting the 339 columns changed completely. The obvious approach is to slice by number range. The interleaving proves that would cut across the real groups.

Phase 3. Building features, and catching our own mistake

Current state
What we knew
  • The block structure of the hidden columns.
  • That time cannot be shuffled and cannot be used raw.
  • Which categories separate fraud from normal.
What we did not know
  • Which columns carry nothing at all.
  • How much of the 339 hidden columns is the same information repeated.
  • Whether the strongest finding from phase 2 was real.
The checks we ran
  • Re-read our own cross tabulation. Phase 2 reported that fraud is 3.75 times more likely when a device record exists. Before building on it we asked the standard question: what else is different about those two groups?
  • Tested every near-empty column against the target before dropping it. For a column that is 99% one value, we looked only at the rows holding something else and measured the fraud rate among them.
  • Correlated columns inside each block, using only the rows where that block is actually present, then kept one column from each tight cluster.
The finding that was wrong

The 3.75 times figure was almost entirely an illusion. One product type never produces a device record, and that same product has the lowest fraud rate and makes up most of the data. So the comparison was mostly measuring the difference between products.

Restricted to the products where the flag actually varies, the real difference is 1.39 times. Still something. Nothing like the headline.

What else came back
  • Several columns that are 99% empty have rare values strongly tied to fraud. They were kept, with the evidence recorded.
  • The hidden columns are heavily redundant inside their blocks, so most can go without losing information.
What changed because of it
  • The wrong number was corrected in the code that writes the report, not just in conversation, so the caveat now travels with the finding permanently.
  • A rescue rule was added to the pruning step. Nothing is dropped for being nearly empty until its rare rows have been checked against the target, and every decision is written to a file with its evidence.
  • All learned transformations became one saved object, fitted only on the earlier 80% of the training period. In production a single transaction arrives with no way to count how common its own card is.
  • The raw time column was excluded from the features. Every test value sits above every training value, so a rule about it fires on everything and separates nothing. Only the repeating parts of time survive.

03

The five moments that redirected the project

If you take nothing else from this document, take these. Each is a small observation with a large downstream consequence.

1

Noticing the test data comes from later in time

A comparison of two date ranges. Thirty seconds of work. It rewrote the validation rule, disqualified a whole family of features, and handed the later monitoring work a real distribution shift to detect instead of a made up one.

compare train and test ranges→no overlap, 30 day gap→never shuffle, never use raw time
2

Comparing patterns instead of counting them

Two columns can be missing the same amount of data and still be unrelated. Grouping by count would have merged two unrelated blocks. Grouping by which exact rows are blank kept them apart and exposed the hidden batch structure behind 339 anonymous columns.

fingerprint the blanks→15 blocks, 8 interleaved→reduce by structure, not by name
3

Refusing the comfortable metric

With a rare outcome, the default measure of success flatters a model that does nothing. Working out what a do-nothing model would score, before training anything, forced a metric with a meaningful floor and a plain business number beside it.

what does a useless model score→96.5%→measure against the base rate instead
4

Asking what else was different about the two groups

The most striking number in the analysis turned out to be a side effect of something else. It was caught only because the earlier stage had been built to print a cross tabulation nobody had asked for. Build the check that could embarrass you.

3.75x looks strong→cross tabulate against everything else→really 1.39x, corrected in writing
5

Imagining a single row arriving in production

One transaction cannot know how common its own card is. That thought experiment turned a pile of preparation steps into one object that learns once, gets saved, and gets loaded again later. It is the difference between a model that works and one that quietly stops matching how it was trained.

picture scoring one row→most steps need remembered facts→save the fitted object, not the script
04

Lookup: if your data does this, do that

The transferable part. None of it depends on fraud, or on this dataset. Scan the left column for something matching your own data.

If you see this in your dataThen do this, and here is why
The outcome you are predicting is rareWork out what a model that always guesses the common answer would score. If that number is high, your usual measure of success is useless. Pick one whose floor is the base rate, and add a plain operational number beside it, such as how much you catch if you can only review 1% by hand.
Your test data comes from a later period than your training dataSplit by time, never at random. Also check every column for whether its test values overlap its training values. Anything that does not overlap cannot be used, because a tree model can only split inside the range it has seen.
Two tables, and only some rows matchKeep every row from the main table, leave the gaps as gaps, add a flag for whether the row matched, then immediately test whether that flag is telling you something new or just repeating a column you already have.
Lots of columns whose meaning is not publishedYou cannot reason about them, so measure them. Look for structure in which rows they are blank on, and in how they move together. Structure you can measure beats meaning you have to guess.
A difference between two groups looks dramaticBefore believing it, cross tabulate those groups against every other major category. Very often the two groups are made of different things and you are measuring that instead.
A column is almost entirely one valueDo not drop it on sight. Look at the minority rows and measure the outcome among them. If your target is rare, a rare value can carry a lot. Record the decision and the evidence either way.
A column holds thousands of codes rather than a few labelsYou cannot expand it into thousands of columns. Count how often each code appears and use the share instead. Rarity itself is usually the signal.
A step needs a statistic computed across many rowsThat statistic must come from training rows only, then be applied unchanged everywhere else. Otherwise the answer sheet leaks into the exam and your score means nothing.
The model will eventually score one row at a timePackage every learned step into a single object that can be saved and reloaded. A script cannot be loaded into a running service. This is the most common way a working model breaks later.
Numbers do not fit comfortably in memoryRead only the columns you need for the question you are asking. Shrink each column to the smallest type that holds its values exactly, and keep an explicit list of the ones where shrinking would silently round something important.
05

Your own worksheet

Work down this list with your own data before writing any modelling code. Every row is a question this project had to answer, phrased so it applies to anything.

Is the data even capable of answering the question?
How many examples of the thing you are predicting do you actually have? Not rows. Examples of the outcome. If the answer is in the low hundreds, fix that before anything else.
Does what arrived match what was promised?
Row counts, column counts, and the rate of the outcome, checked against whatever documentation you have. Put these in a script, not a notebook, so they can be rerun forever.
Is the key you are joining on unique?
If it is not, your join can quietly multiply rows and every number after it is wrong. Make the code refuse to proceed if this ever changes.
Do the same columns have the same names everywhere?
Spelling differences between files are common and surface much later as missing columns. Find them now and handle them deliberately.
Where does time run in this data?
Find the earliest and latest point in each file. If your test data sits after your training data, everything about your validation changes.
What would a useless model score?
Compute it before training anything. It tells you which measures of success are meaningless here and gives you the floor to compare against.
Is missing data damage or information?
Compare the outcome rate for rows that have a value against rows that do not. Then check whether that difference is really about something else.
Which columns carry nothing?
One value throughout is an easy drop. Nearly one value is not: check the minority rows against your outcome first, and write down what you found.
What structure is hiding in the columns you cannot read?
Group them by which rows they are blank on, then look at how they move together inside each group. Keep one representative from each tight cluster.
What will not exist at prediction time?
Walk through one single row arriving on its own. Anything it cannot compute for itself has to be learned in advance and saved.
Where should each new file live?
Ask what kind of thing it is, not what stage made it. How something is done goes with the helpers, what order things happen goes with the pipelines, output for people goes with the reports, output for machines goes with the models.
What do you still not know?
List it, number it, and tag each one with the stage that will need the answer. Chase the ones that block work. Let the others wait in the open.
06

Habits that made the difference

These are cheap. None of them require skill. All of them saved time.

Verify before you build

The first real script in the project was the one that proves the data is sound. It runs in seconds and has been rerun after every change since.

Turn findings into checkpoints

Once a number is measured, every later stage recomputes it. If it ever stops matching, something upstream broke and you find out in the same minute.

Build the whole folder structure on day one

Including the folders that stay empty for months. Nothing ever has to be reorganised mid-project, and every stage already knows where its output belongs.

Let the code write the report

Written summaries are generated from the actual numbers, so they cannot quietly go out of date. When a finding was corrected, the fix went into the generator.

Give every decision an identifier

Numbered decisions with their reasons beside them. Six weeks later you can ask why something is the way it is and get an answer rather than a shrug.

Record what you dropped

Every removed column was written to a file with the evidence behind the removal. That is the difference between pruning and losing things.

Correct yourself in public

When an earlier claim turned out to be misleading, the next document said so plainly and explained the mistake.

Build the check that could embarrass you

The cross tabulation that exposed the biggest error was not required by anything. It was added because it might contradict us, and it did.

Assume you will move everything

Nothing hardcoded, paths worked out at run time, versions pinned exactly. The project has already been moved once with no code changes.
