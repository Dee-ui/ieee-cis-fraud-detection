reports/Output for humans, as opposed to models/ which is read by machines.

01

The engine underneath everything

Every phase ran the same five moves. Once you see the loop, the rest of this document is the loop repeated with different content and different files falling out of it.

MOVE 1Name the gap

Write down what you do not know. As a question with an answer you could go and find.

MOVE 2Go measure it

Write a small piece of code that answers it and prints the number. Do not reason from memory.

MOVE 3Read what came back

Including the parts you did not expect. Surprises are where the real decisions hide.

MOVE 4Decide, and say why

Give the decision a number, put the evidence beside it, and write the file that implements it.

MOVE 5Lock it and move on

The number becomes a checkpoint. Later stages recheck it, so a break shows up immediately.

Anything you could not answer becomes a numbered open question, tagged with the phase that will need it. Nothing gets forgotten and nothing gets guessed.

Phase 0. Choosing what to work on

Before any code
What we knew
  • An earlier attempt at the same problem had stalled. The model would not improve whatever technique was tried.
  • That dataset had 193 fraud cases inside 9,940 rows.
What we did not know
  • Whether the ceiling was the method or the data.
  • What a dataset needs to look like for the problem to be worth solving properly.
The check we ran

We wrote down what the project needed to demonstrate, then looked for data that would force us to demonstrate it: enough real fraud to learn from, more than one table so there is a genuine join, and a test set separated in time so the hard lesson about validation cannot be dodged.

What came back
  • 20,663 fraud cases in 590,540 rows. Roughly a hundred times more examples of the thing we are detecting.
  • A second table of device information matching only some transactions.
  • A test period starting a month after training ends.
What changed because of it

The project became possible at all, and it set the habit for everything after: choose your inputs by the shape of the problems you want to be forced to solve, not by the topic. Every awkward property of this data later became one of the most interesting parts of the work.

Phase 1. Proving the data before trusting it

Foundations
What we knew
  • The published row and column counts for each file.
  • Our own machine and platform.
What we did not know
  • Whether the download was complete and matched what was published.
  • Whether the identifier linking the two tables is unique, which decides whether a join is safe.
  • How much of the second table actually matches the first.
  • Where the project folder would eventually live.
The check we ran

Before touching the data, we wrote a script whose only job is to prove the data is sound. Five checks: every file present and not empty, row and column counts against the published figures, the fraud rate roughly as advertised, no duplicate identifiers, and consistent column spelling across files. It reads one column at a time rather than loading whole files, so it costs seconds instead of gigabytes.

What came back
  • Fraud rate 3.4990%. Every shape matched exactly.
  • Zero duplicate identifiers in either table.
  • Only 24.4% of transactions have a matching record in the second table.
  • Test files spell a set of columns with a hyphen where training files use an underscore.
What changed because of it
  • Those numbers became permanent checkpoints, recomputed by every later stage.
  • Because the identifier is unique, the join could be set to fail loudly if that ever stopped being true.
  • The spelling difference became a deliberate rename step instead of a confusing bug later.
  • Because the folder location was unknown, no path was ever written by hand. That paid off twice: once when the folder name did not match, once when the whole project was moved.

Phase 2. Understanding before touching

Exploration
What we knew
  • The verified counts from phase 1.
  • That most columns are anonymised and their meaning will never be published.
What we did not know
  • Whether three quarters of the second table being missing is damage or information.
  • Whether time matters, and how.
  • Whether 339 unnamed columns have any structure at all.
  • Which measure of success would actually tell us if the model is any good.
The checks we ran
  • Sorted every column into a family by a naming rule, and made the code shout if anything did not fit. Nothing was allowed to slip through unclassified.
  • Compared the time range of training against test.
  • Fingerprinted each column's pattern of blanks rather than counting them. Same fingerprint means blank on exactly the same rows.
  • Measured the fraud rate inside every category, with a minimum group size so a category of three transactions cannot shout louder than one of three hundred thousand.
What came back
  • Training covers December to May, testing July to December. A deliberate 30 day gap and no overlap.
  • The 339 unnamed columns fall into exactly 15 blocks that go blank together. Eight weave through each other's numbering.
  • Two blocks are both 86.12% empty but in different rows. Counting blanks would have merged them.
  • Categories separate strongly. One product runs at 11.69% fraud while another runs at 2.04%.
What changed because of it
  • Validation became time based. Shuffling would let the model learn from the future and be graded on the past.
  • Accuracy was dropped entirely. A model that says "never fraud" is right 96.5% of the time here.
  • Blanks stay blank. The models we intend to use learn a direction for missing values on their own.
  • The plan for cutting the 339 columns changed completely. Slicing by number range would cut across the real groups.

src/utils/ingestion_utils.pyNEW

One function per operation involved in getting two tables into one.

  • Loads a file, reading the whole column before deciding its type.
  • Renames the hyphen columns to match the underscore ones.
  • Marks every row that came from the second table, before joining.
  • Joins, keeping every transaction and leaving blanks where there was no match.
  • Refuses to run if the join key ever stops being unique, because a silently bigger table is worse than a crash.
  • Saves in a format that remembers column types, unlike a plain text file.
src/pipelines/ingestion.pyNEW

Says what happens in what order, and nothing else.

  • Six steps: load both tables, fix names, mark and join, check the shape, shrink, save.
  • Training and test go through this one path, with their differences passed in as settings.
  • Carries the expected row and column counts, so a wrong shape stops the run.

Why one path Two separate scripts would drift apart, and the difference would show up as a broken model.

Phase 3. Building features, and catching our own mistake

Feature engineering
What we knew
  • The block structure of the hidden columns.
  • That time cannot be shuffled and cannot be used raw.
  • Which categories separate fraud from normal.
What we did not know
  • Which columns carry nothing at all.
  • How much of the 339 hidden columns is the same information repeated.
  • Whether the strongest finding from phase 2 was real.
The checks we ran
  • Re-read our own cross tabulation. Phase 2 reported that fraud is 3.75 times more likely when a device record exists. Before building on it we asked: what else is different about those two groups?
  • Tested every near-empty column against the target before dropping it. For a column that is 99% one value, we looked only at the rows holding something else and measured the fraud rate among them.
  • Correlated columns inside each block, using only the rows where that block is present, then kept one column from each tight cluster.
The finding that was wrong

The 3.75 times figure was almost entirely an illusion. One product type never produces a device record, and that same product has the lowest fraud rate and makes up most of the data.

Restricted to the products where the flag actually varies, the real difference is 1.39 times. Still something. Nothing like the headline.

What else came back
  • Only 2 columns were dropped. 22 were rescued. One of them holds the same value on 99.71% of rows, but on the remaining 1,370 rows nearly half are fraud.
  • Another rescued column works in reverse: when it is not zero, fraud almost never happens. It survived only because the rule was written to catch unusually safe values too.
  • The hidden columns are heavily redundant. 337 reduced to 137, and unevenly: one block kept 2 of 11, another kept 24 of 42.
What changed because of it
  • The wrong number was corrected in the code that writes the report, not just in conversation, so the caveat now travels with the finding permanently.
  • Nothing gets dropped without evidence. Every decision, keep or drop, is written to a file with the numbers behind it.
  • All learned transformations became one saved object, fitted only on the earlier 80% of the training period. In production a single transaction arrives with no way to count how common its own card is.
  • The raw time column was excluded from the features. Every test value sits above every training value, so a rule about it fires on everything and separates nothing.
Files createdPHASE 3 · A NEW PACKAGE, A SAVED OBJECT, DATA VERSIONING
src/utils/column_selection.pyNEW

Decides which columns survive, and records why.

  • Finds columns holding only one value. Nothing to split on, so they go.
  • Finds columns where one value covers 99% of rows, and flags them as candidates.
  • For each flagged column, checks the minority rows: if fraud among them is far above or far below normal, the column is rescued.
  • Inside each hidden block, groups columns that move together and keeps the one with the most distinct values.
  • Returns the evidence with every decision, rather than just a list of names.

The rescue matters A blanket "drop anything 99% constant" rule would have deleted the sharpest single signal in the dataset.

src/utils/feature_utils.pyNEW

Small builders that turn raw columns into things a model can use.

  • Time becomes hour of day and day of week, the parts that repeat.
  • The amount becomes three things: its logarithm, its cents, and whether it is a round number.
  • An email domain splits into provider and suffix, so three variants of one provider stop looking unrelated.
  • A screen size like "1920x1080" becomes width, height, and area.
  • Messy device text is reduced to its first word, collapsing hundreds of values into a handful.
  • One shared function converts any column to text in exactly one way, so training and test cannot produce different labels for the same value.

None of these learn anything They do the same thing to any row, so none can leak.

src/features/engineer.pyNEW

The transformer. Learns once, remembers, and applies the same thing forever after.

  • Learning phase: counts how often each value appears, assigns a number to each text value, and works out the average amount within each group.
  • Applying phase: looks those answers up. A value never seen before gets a reserved code, and an unknown group gets a count of zero.
  • Learning and applying share the same internal code, so the two cannot drift apart.
  • The output column list is fixed by actually running the transformation once during learning, not by predicting it separately.
  • Builds a rough customer fingerprint from card, address, and first-seen day, but only uses it for grouping, never as a feature.

Why an object, not a script One transaction arriving at a web service cannot count how common its own card is. That answer must have been saved.

src/pipelines/features.pyNEW

Runs the stage, then checks four things that would otherwise fail silently.

  • Cuts the training data by time and labels each row train or validation.
  • Learns on the earlier portion only, then applies to everything.
  • Check one: the answer is not hiding among the features.
  • Check two: training and test have identical columns in identical order.
  • Check three: no column is blank on every row.
  • Check four: nothing contains infinity, which a division can easily produce.

Why these four Each has silently ruined a model somewhere. None of them raises an error on its own.

Phase 4. Training, and turning a score into money

Modelling
What we knew
  • 284 features, split by time, with a saved transformer behind them.
  • That six of those features are blank on 82% of the data we actually want to score.
  • The measure of success, chosen two phases earlier.
What we did not know
  • Which model family wins, and whether the complicated ones beat a simple one at all.
  • Whether those six fragile features are worth keeping.
  • What the model is actually worth, in money, to someone who has to pay for it.
  • Where to set the threshold, since the usual 0.5 is arbitrary.
The checks we ran
  • Built a cost model with five stated assumptions. What an analyst review costs, what a dispute fee costs, the friction of a false alarm, how much flagged fraud is actually stopped, and how many cases the team can handle. Every one written down so it can be argued with.
  • Trained five candidates, two of them deliberately weak. A model that predicts the same thing for everyone, and a plain linear model. The weak ones are not filler: they set the floor.
  • Wrote down the rule for the fragile features before running the experiment. Retrain without them; if the cost is under a stated amount, drop them.
  • Cross-validated across expanding time windows. Each fold trains on more history than the last and is scored on the period straight after.
What came back
  • The do-nothing model scored exactly the fraud rate and exactly 0.5, which proves the measuring code itself is correct.
  • Two boosted models were close, and the two metrics disagreed about which won. The one better at the top of the ranking took it, because that is where the review queue lives.
  • One candidate never finished improving inside its round budget, so its score understates it.
  • The fragile features cost more than the stated tolerance to remove, so the rule said keep.
  • The device flag from phase 3 ranked 270th of 284, with an influence of exactly zero. The earlier prediction was right.
The result nobody expected

Across the four time folds the score climbed as training data grew, then dropped on the final fold, which had the most data of all.

More data made it worse. That cannot be a data-volume story. Something about the most recent period is simply harder to predict, which means model quality is not a fixed property. It moves with the period being scored.

What changed because of it
  • The threshold is now chosen by money, not convention. The cost of every possible cut-off is computed exactly, weighted by real transaction amounts, and the cheapest point within the team's capacity is picked.
  • Every run is recorded automatically: settings, results, the model file, and which code version produced it. The comparison table is now something you sort in a web page rather than rebuild by hand.
  • The chosen model gets a name and a pointer in a catalogue, so deploying later means moving a pointer rather than editing code.
  • The failing fold made monitoring non-optional. If quality varies by period, you cannot know how the model is doing from the number it scored at training time.
Files createdPHASE 4 · METRICS, CANDIDATES, TRACKING, THE TRAINING STAGE
src/utils/metrics.pyNEW

Every number this project reports, in one place.

  • Ranking scores: how well the model orders transactions by risk.
  • Review-rate scores: if the team reviews the riskiest 1%, how much fraud do they catch.
  • The cost model: prices all four outcomes at every possible cut-off.
  • Does it by sorting once and taking running totals, so it is exact rather than sampled, and takes under a second.
  • Weights by the real transaction amount, so a missed large fraud counts more than a missed small one.
  • Reports both the cheapest cut-off overall and the cheapest one the team can actually staff.

Why one file Every model is scored identically, so a difference between two models is the model, not the measuring.

src/models/candidates.pyNEW

The list of models to try, and the small differences between them.

  • Each library stops training early in its own way. A tiny adapter per library hides that.
  • The pipeline then treats all five identically, and adding a sixth is one entry here.
  • Includes a deliberately useless model, whose score is known in advance and therefore checks the ruler.
  • Includes a plain linear model, so the complicated ones have to earn their complexity.
  • Has a helper that rebuilds a model with a fixed number of rounds, for retraining with no held-out data to stop against.
  • Builds the time-based folds: each trains on everything up to a point and is scored on what comes next.
src/utils/mlflow_utils.pyNEW

Sets up run tracking, and smooths over library churn.

  • Points the tracker at a single local database file, with forward slashes so it works on any platform.
  • Inspects the logging function and uses whichever argument name this version accepts.
  • Truncates over-long settings so one long value cannot fail an entire run's record.
  • Skips anything that is not a real number when logging results.

The pattern When a library is mid-transition, check what is actually installed rather than assuming.

src/utils/model_plots.pyNEW

Five charts, one per question a reader will ask.

  • How the candidates compare, with the random floor drawn in.
  • The trade-off curve: catch more fraud, annoy more customers.

Phase 5. Making it hard to break

Current state
What we knew
  • A chosen model, a threshold, and an importance ranking.
  • Two shifts between training and test that we had already measured.
  • That model quality dropped in the most recent period we could check.
What we did not know
  • Whether the code still behaves correctly after anyone changes it.
  • How to tell the model is failing when labels will not arrive for months.
  • Whether the rare-but-decisive columns rescued in phase 3 actually earned their place.
  • What, if anything, prevents a bad model reaching production.
The checks we ran
  • Worked the cost model out on paper for four transactions, then asserted the code produces the same answer to the penny.
  • Asserted that transforming one row gives the same answer as transforming a batch containing it. If that ever stops being true, something has started depending on which rows travel together.
  • Compared every month of the unlabelled period against the training distribution, bucket by bucket, rather than just counting blanks.
  • Looked at the registry to see what was actually in it.
Four things we got wrong
  • We measured importance with the wrong tool. The rescued column ranked near the bottom, because average influence across all rows is near zero for something that only speaks on 0.3% of them. On a 5,000 row sample that is about 14 rows.
  • A throwaway test model had registered itself as version 1 of the production catalogue. Nothing stopped it, and nothing downstream could tell it apart from a real one.
  • The readme quoted a 42-day saving as an annual figure, understating the result by a factor of nine.
  • The headline recall was being read as money. The model catches 44.6% of fraud cases but only 31.2% of fraud value, because a large fraudulent purchase looks much like a large legitimate one.
What the monitoring found
  • The fragile feature family carries about a tenth of the model's total explanatory weight, and is blank on most of the data it will score. That is now the top production risk.
  • One of those features never goes blank at all. When it has nothing to say it quietly returns zero, so a missing-value check sees a perfectly healthy column while most of its rows carry no information.
What changed because of it
  • Importance is now recorded two ways: the average influence, and the loudest influence. The second is what finds a signal that is rare but decisive, which in fraud is a whole category of the best signals.
  • Drift is measured on whole distributions, not just blanks, because a feature can collapse onto one value without ever going missing.
  • Drift is weighted by how much the model relies on each feature. A raw count of drifted features fires every month and gets ignored, which is worse than no alarm.
  • Deployment became a separate, deliberate command with six gates. Training says "here is a candidate". Promotion says "this is fit to serve". Different decisions, different evidence.
  • Every number now has a test behind it, and those tests run on a clean machine every time code is pushed.

03

The moments that redirected the project

If you take nothing else from this document, take these. Each is a small observation with a large downstream consequence.

1

Noticing the test data comes from later in time

A comparison of two date ranges. Thirty seconds of work. It rewrote the validation rule, disqualified a whole family of features, and handed the later monitoring work a real shift to detect instead of a made up one.

compare train and test ranges→no overlap, 30 day gap→never shuffle, never use raw time
2

Comparing patterns instead of counting them

Two columns can be missing the same amount of data and still be unrelated. Grouping by count would have merged two unrelated blocks. Grouping by which exact rows are blank kept them apart and exposed the hidden structure behind 339 anonymous columns.

fingerprint the blanks→15 blocks, 8 interleaved→reduce by structure, not by name
3

Asking what else was different about the two groups

The most striking number in the analysis turned out to be a side effect of something else. It was caught only because the earlier stage had been built to print a cross tabulation nobody had asked for. The model later confirmed it, ranking that feature 270th of 284 with an influence of exactly zero.

3.75x looks strong→cross tabulate against everything else→really 1.39x, and the model agreed
4

Checking the rare rows before deleting a column

A column holding the same value on 99.7% of rows looks like an obvious deletion. On the 1,370 rows where it differed, nearly half were fraud. The rule that saved it also had to work in reverse, and it did: another column was kept because its rare value meant fraud almost never happens.

99% one value→measure the minority rows→2 dropped, 22 rescued
5

Imagining a single row arriving in production

One transaction cannot know how common its own card is. That thought experiment turned a pile of preparation steps into one object that learns once, gets saved, and gets loaded again later. A test now asserts that one row and a batch give the same answer.

picture scoring one row→most steps need remembered facts→save the fitted object, not the script
6

Training a model whose score you already know

A model that predicts the same thing for everyone must score exactly the base rate and exactly 0.5. Both came out right, which proved the measuring code was sound before any real result was trusted. Without that, a subtle bug in the metrics would have made every comparison meaningless and nothing would have looked wrong.

train a deliberately useless model→it scores exactly what it must→the ruler is proven, now measure
7

More data made the model worse

Across four time folds the score climbed, climbed, climbed, then dropped on the fold with the most training data of all. That cannot be a volume story, so it must be a period story: the recent months are simply harder. Model quality is not a fixed property of the model, and that single observation is what makes monitoring necessary rather than decorative.

expanding time folds→the biggest fold scored second worst→you cannot trust a training-time number
8

Discovering the wrong measuring stick, twice

Average importance said the rescued column was worthless. But an average across all rows is near zero for something that only speaks on 0.3% of them. Separately, a missing-value check called a broken feature healthy, because when it has nothing to say it returns zero rather than a blank. Both failures look like good news, which is what makes them dangerous.

the number looks fine→ask what the number averages over→measure the loudest case, and whole distributions
9

A throwaway test model registered itself

A fast run made to check the code worked ended up as version 1 in the catalogue of deployable models. Nothing downstream could tell it apart from a real one. The fix was not to delete it but to make the mistake impossible: label every run with its mode, refuse registration from a test run, and put six gates in front of production.

look at what is actually in the registry→a 150-round test model→promotion becomes a separate, gated decision
04

Lookup: if your data does this, do that

The transferable part. None of it depends on fraud, or on this dataset. Scan the left column for something matching your own situation.

If you see thisThen do this, and here is why
The outcome you are predicting is rareWork out what a model that always guesses the common answer would score. If that number is high, your usual measure of success is useless. Pick one whose floor is the base rate, and add a plain operational number beside it.
Your test data comes from a later period than your training dataSplit by time, never at random. Also check every column for whether its test values overlap its training values. Anything that does not overlap cannot be used, because a tree model can only split inside the range it has seen.
Two tables, and only some rows matchKeep every row from the main table, leave the gaps as gaps, add a flag for whether the row matched, then immediately test whether that flag is telling you something new or repeating a column you already have.
Lots of columns whose meaning is not publishedYou cannot reason about them, so measure them. Look for structure in which rows they are blank on, and in how they move together. Structure you can measure beats meaning you have to guess.
A difference between two groups looks dramaticBefore believing it, cross tabulate those groups against every other major category. Very often the two groups are made of different things and you are measuring that instead.
A column is almost entirely one valueDo not drop it on sight. Look at the minority rows and measure the outcome among them, in both directions: unusually risky and unusually safe are both signals. Record the decision either way.
A column holds thousands of codes rather than a few labelsCount how often each code appears and use the share instead. Rarity itself is usually the signal.
A step needs a statistic computed across many rowsThat statistic must come from training rows only, then be applied unchanged everywhere else. Otherwise the answer sheet leaks into the exam.
The model will eventually score one row at a timePackage every learned step into a single object that can be saved and reloaded, and write a test asserting one row gives the same answer as a batch. A script cannot be loaded into a running service.
You need to choose a thresholdPrice every outcome, then compute the total cost at every possible cut-off and pick the cheapest one your team can actually staff. The default 0.5 is a convention, not an answer. Weight by the size of each case, not just the count.
You are about to trust a metricRun something whose score you already know, like a model that predicts one constant. If it does not produce the exact number it must, the measuring code is broken and every comparison after it is meaningless.
An important feature is mostly unavailable on new dataMeasure how much weight the model gives it, then decide with a rule written down before you run the experiment. A rule chosen after seeing the result is a justification, not a rule.
A feature matters enormously but rarelyAverage importance will hide it, because the average includes every row where it says nothing. Look at its loudest influence, or average only over the rows where it fires.
You will not get labels for weeks or monthsWatch the inputs instead. Compare each new period against the training distribution and treat a large shift as a warning that the outputs are about to go wrong.
You are checking for broken features by counting blanksNot enough. A feature can collapse onto a single value without ever going missing, which looks perfectly healthy. Compare whole distributions instead.
An alarm covers hundreds of featuresWeight each one by how much the model relies on it. A raw count fires constantly and gets ignored, which is worse than having no alarm.
You have a fast test modeMake sure it cannot write to anything downstream. A quick run that registers a model, saves an artifact, or overwrites a report is indistinguishable from a real one later.
Something is ready to go liveMake promotion a separate, deliberate command with explicit checks. Producing a candidate and declaring it fit to serve are different decisions with different evidence.
05

Your own worksheet

Work down this list with your own data. Every row is a question this project had to answer, phrased so it applies to anything.

Is the data even capable of answering the question?
How many examples of the thing you are predicting do you actually have? Not rows. Examples of the outcome. If the answer is in the low hundreds, fix that before anything else.
Does what arrived match what was promised?
Row counts, column counts, and the rate of the outcome, checked against whatever documentation you have. Put these in a script, not a notebook, so they can be rerun forever.
Is the key you are joining on unique?
If it is not, your join can quietly multiply rows and every number after it is wrong. Make the code refuse to proceed if this ever changes.
Where does time run in this data?
Find the earliest and latest point in each file. If your test data sits after your training data, everything about your validation changes.
What would a useless model score?
Compute it before training anything. It tells you which measures of success are meaningless and gives you the floor to compare against. Then actually train that useless model, to prove your measuring code is right.
Is missing data damage or information?
Compare the outcome rate for rows that have a value against rows that do not. Then check whether that difference is really about something else.
Which columns carry nothing?
One value throughout is an easy drop. Nearly one value is not: check the minority rows against your outcome first, and write down what you found.
What structure is hiding in the columns you cannot read?
Group them by which rows they are blank on, then look at how they move together inside each group. Keep one representative from each tight cluster.
What will not exist at prediction time?
Walk through one single row arriving on its own. Anything it cannot compute for itself has to be learned in advance and saved.
What does being wrong actually cost?
Put a number on each kind of mistake, write down where each number came from, and keep them all in one settings file. Then the threshold is an answer rather than a convention.
How will you know it is still working?
If labels arrive months late, you cannot check the outputs. Decide now what you will watch on the inputs, and what number would make you retrain.
What must be true before this goes live?
Write the checks down as a list, then make them a command someone has to run. Include at least one that would have caught the last mistake you made.
Where should each new file live?
Ask what kind of thing it is, not what stage made it. How something is done goes with the helpers, what order things happen goes with the pipelines, output for people goes with the reports, output for machines goes with the models.
What do you still not know?
List it, number it, and tag each one with the stage that will need the answer. Chase the ones that block work. Let the others wait in the open.
06

Habits that made the difference

These are cheap. None of them require skill. All of them saved time.

Verify before you build

The first real script in the project was the one that proves the data is sound. It runs in seconds and has been rerun after every change since.

Test the ruler before the thing you measure

Run something whose answer you already know. Every number that follows depends on the measuring code being right, and nothing else would reveal it if it were not.

Turn findings into checkpoints

Once a number is measured, every later stage recomputes it. If it stops matching, something upstream broke and you find out in the same minute.

Build the whole folder structure on day one

Including the folders that stay empty for months. Nothing has to be reorganised mid-project, and every stage already knows where its output belongs.

Write the decision rule before the experiment

A tolerance chosen in advance decides. A tolerance chosen afterwards justifies. Only one of those is worth anything.

Let the code write the report

Written summaries are generated from the actual numbers, so they cannot quietly go out of date. When a finding was corrected, the fix went into the generator.

Give every decision an identifier

Numbered decisions with their reasons beside them. Six weeks later you can ask why something is the way it is and get an answer rather than a shrug.

Record what you dropped

Every removed column was written to a file with the evidence behind it. That is the difference between pruning and losing things.

Correct yourself in public

Four claims in this project turned out to be wrong. Each was named plainly in the next document, with the arithmetic that showed it.

Build the check that could embarrass you

The cross tabulation that exposed the biggest error was not required by anything. It was added because it might contradict us, and it did.

Fix the class of mistake, not the instance

A test model reached the registry. The fix was not deleting it, it was labelling every run and putting gates in front of production so it could not happen again.

Assume you will move everything

Nothing hardcoded, paths worked out at run time, versions pinned exactly. The project has already been moved once with no code changes.
